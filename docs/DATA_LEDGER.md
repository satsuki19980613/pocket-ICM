# データ管理台帳

ゲーム由来の数値（プライズ・開始スタック・人数・ブラインド・丸め）を **一元管理**するための台帳。

## この台帳の約束

1. **数値の実体はコードに 1 か所だけ置く。** この台帳は「その数値がどこにあるか・どこから来たか・
   どれくらい確かか」を記録する。台帳に数値を書き写すのは**一覧性のためだけ**で、正本はコード。
2. **台帳とコードがずれたらテストが落ちる。** `packages/core/test/dataLedger.test.ts` がこのファイルの
   モード表を読み、`GAME_MODE_SPECS` と突き合わせる。数値を変えるときは**コードと台帳の両方**を直す。
3. **出典と日付を必ず書く。** 公式ページは予告なく消える（実際に旧ランク戦解説 `/news/explain0001/` は
   404 になり、クラブマッチの古いシーズン告知も軒並み消えている）。確度の欄は将来の自分への申し送り。
4. **推測値は載せない。** 確定できないものは「未確定」の節に理由つきで残し、コードにも入れない。

### 注意（踏むと痛い落とし穴）

- **総チップはモード間で衝突する。** `rank-4` = `club` = 90000、`rank-5` = `legend-*` = 120000。
  よって**総チップからゲームを自動判定してはならない**。判定は UI のゲーム選択だけを根拠にする。
- **レジェンドの 6 人ペイアウトはゼロサム**（総和ちょうど 0）。求解の早期終了しきい値を
  「payout の総和」に比例させると 0 になって永久に止まらない。**振れ幅（max−min）**を使うこと。
- **レジェンドは 1 試合でレートが 2 本同時に動く。** シーズンレート（月次リセット・初期 200・0 で即時降格）と
  ベースレート（恒久・卓平均との差で補正。補正は順位に依存しない＝戦略に影響しない）。
  4 位はシーズン ±0 だがベース −7 で、2 つは目的関数として食い違う。既定は素点平均。
- **HU（2 人）はどのモードでも戦略が同じ**（2 着払いは必ずアフィン等価）。HU 表は全モードで流用可。
- **事前計算表（3 人表 / 4 人表 / 5 人 NN）はクラブのプライズを焼き込んである。** 他モードは表を使わず
  厳密求解に回す。表を他モード用に作るなら 1 セット約 13.5MB ＋生成数時間。

### SIT & GO の開始スタック

正本: [`packages/sng/src/types.ts`](../packages/sng/src/types.ts) の `START_BBS` / `BASE_BB`（SPEC §7.4.7）

| 開始スタック（BB） | チップ |
|---|---|
| 75 | 15,000 |
| 100 | 20,000 |
| 150 | 30,000 |
| 200 | 40,000 |

レベル 1 の BB を 200 チップ（本台帳§2 の 3 構造すべてで共通）として、`BB × 200` でチップに換算する。
獲得 pt は**新しい表を持たず**、本節の `GAME_MODE_SPECS`（作成時に選んだゲームモード）の順位別プライズを
**参加人数ぶんだけ先頭から**切って使う（例: 2 人戦のクラブマッチなら先頭 2 つ `+5 / +3`）。

## 2. ブラインド構造

正本: [`packages/core/src/blindStructure.ts`](../packages/core/src/blindStructure.ts)（生表の 3 構造）。
`packages/ocr/src/blindLevels.ts` はこれを再エクスポートするだけで、生表を独自に持たない。

**全モード共通**（SIT & GO を含む）。SB = BB/2、アンティは全員払いでおよそ 0.25×BB（ただし式では
作れないので表の値を使う）。モードによる違いは**上昇間隔と開始スタックだけ**で、bb 単位の局面には
現れない。SIT & GO（SPEC §7.4.7）も自前の表は持たず、この同じ 3 構造（通常 / ゆっくり /
もっとゆっくり）をそのまま使う。

| 構造 | レベル数 | 用途 | 出典 |
|---|---|---|---|
| 通常 | 16 | ランク戦（3 分）/ レジェンドマッチ（4 分）/ クラブマッチ（5 分） | 公式 `/news/structure/` ＋ さつき提供の構造表 |
| ゆっくり | 32 | フレンド戦 | さつき提供（ゆっくりFIX-1.png） |
| もっとゆっくり | 59 | フレンド戦 | さつき提供（もっとゆっくりver2.png） |

- 読み取った BB は**相対 2% 以内**でのみ表にスナップする（緩めると別スピードの近いレベルへ誤スナップし、
  総チップ保存が壊れる。実測で 800 を 780 へ誤スナップした事故あり）。
- どの表にも当たらない BB は**読み値をそのまま採用**（level=0）。

## 3. BB 表示の丸め

正本: [`packages/core/src/bbDisplay.ts`](../packages/core/src/bbDisplay.ts) の `roundBbDisplay` / `formatBbDisplay`

ゲームは bb 換算の値を**小数第 2 位で四捨五入して小数第 1 位まで**表示する（29.25 → 29.3）。
実測で確定（公式 Web 版・BB 200 のチップ表示と BB 表示の組から）。末尾の `.0` は表示しない。

**bb を画面に出すところは必ず `formatBbDisplay` を通す。** 素通りすると実機に存在しない桁が出る
（例 42.15bb）。素通りを防ぐ見張りテスト: `packages/app/src/components/bbDisplayUse.test.ts`。
EV・EV ロスの **pt は別尺度**なので小数第 3 位まで（この丸めは適用しない）。

## 4. 読み取れなかったスタックの扱い

正本: [`packages/ocr/src/chipConsistency.ts`](../packages/ocr/src/chipConsistency.ts)

| 未読の席数 | 挙動 |
|---|---|
| 0 席 | 合計が理論値と合うか検算。表示丸めの残差ぶんは触らない |
| **1 席** | 総チップから逆算して**補正する**。ただし値は選んだゲームに依存するので確認画面で注意を出す |
| **2 席以上** | **補正しない**（一意に解けない）。仮値 0bb のまま、確認画面で**修正を促す** |

1 席の復元は「未読席が差分を丸ごと吸収する」構造上、**総チップ照合では取り違えを検出できない**
（同じフレームで club 10.9bb / legend 42.15bb と 4 倍違っても検算は通る）。だから隠さず見せる。

## 7. 本番の確認手順

配信は `.env.local` のあるローカルから `npx wrangler deploy`（詳細は [`DEPLOY.md`](../DEPLOY.md)）。
デプロイ後は毎回これで確認する（PWA のキャッシュに惑わされないため curl で見る）:

```bash
URL=https://pocket-icm.wsk641.workers.dev
curl -s $URL/ | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'   # ローカルの dist と同じ名前か
curl -s $URL/assets/index-XXXX.js | grep -c 'supabase.co'    # 1 なら設定済み・0 なら壊れたビルド
```

バンドル名は内容のハッシュなので、**名前が一致＝中身が一致**。
