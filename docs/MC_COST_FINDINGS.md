## 結論（設計判断）

1. **§3.3 の字義どおりの「ハンドクラス組ごとの着順分布キャッシュ」は破綻する。**
   3-way ですら未圧縮 50MB（PWA 同梱には重い）、4-way 10GB、5-way 2.4TB。同梱も生成も非現実的。

2. **求解時に per-class-tuple で MC するのも R^k 爆発で不可**（3-way R=80 で 1パス ~1000s）。

3. **採用方針: ノードレベルのレンジ MC。** 各ショーダウン・ノードで参加者のレンジから
   ハンドを引き（衝突は棄却）ボードを引いて評価するのを S 回。コストは **O(S)** で
   レンジ幅・人数に依存しない（実測 1ノード ~70-110ms / S=100k）。push/fold のゲーム
   ツリーはノード数が小さい（PU/CA/OC の枝）ため、1スポットの求解は数百 ms〜数秒に収まる見込み。
   ただし FP は反復ごとに戦略が変わるため、ナイーブに毎反復フル MC すると反復数×ノード数×100ms。
   → M3 で「戦略更新のたびに全再サンプルしない」工夫（共通乱数・equity の再利用、
   もしくは all-in equity を先に MC 見積りして FP は決定論的に回す）を設計する。

4. **MC 設定（T-8 確定）**: シード・サンプル数は `packages/solver/src/mcConfig.ts` に明文化。
   既定 `NODE_MC_SAMPLES = 100_000`、`MC_SEED` 固定。人数での傾斜は不要（O(S) のため）。

## M3 への申し送り（→ M3 で対応済み）

- §3.3 の「クラス別キャッシュ」記述は**ノードレベル レンジ MC に置換**。
  → **対応済み**: SPEC §3.3-4 を改訂（さつき承認）。実装は `packages/solver/src/showdownMc.ts`。
- FP × MC の組み合わせ方（equity 先取り MC）が 3〜6人求解の中核設計になる。
  → **対応済み（3-way）**: `multiwaySolver.ts`。epoch ごとに現在レンジで all-in equity を MC 見積りし、
     FP 反復はその見積りで決定論的に回す。4〜6人は続くステップ。
- 4+ way ノードは出現頻度が低く、§4.3 が MC ノイズ床の基準緩和を許容している。

## M3 追記（2026-09-01）

- **RNG 品質の是正**: `DeterministicRng` を xorshift128+ の 32bit 変種から **mulberry32** に置換。
  旧実装は高位ビットの分布が弱く、`showdownMc` のレンジ抽選（[0,1) 浮動小数・大きな法の剰余）で
  クラス抽選が偏った（AA 等の小バケットが引かれない）。mulberry32 は全ビットに良好なアバランチを持ち、
  `nextInt`（低位）にも `nextFloat`（全ビット）にも安全。placement MC の厳密一致テストは緩和無しで通過し、
  収束もむしろ改善。シード決定性の契約は不変。
- **3-way exploitability の構造的な床**: 反復数を増やしても（600→8000）、サンプル数を増やしても（80k→800k）、
  ノードレベル MC 求解の exploitability は **~0.01pt（実払いプール10pt 比 ~0.1%）** で下げ止まる。
  原因はクラス別 equity 推定のバイアス + アクション確率のカードリムーバル近似。SPEC §3.1 の理想 0.05%
  （0.005pt）を上回るため、`solveThreeWay` の既定収束しきい値は床の上（プール比 0.15%）に置き、均衡解でも
  常時「収束不十分」にならないようにした（§4.3 のマルチウェイ緩和に整合）。**推定量のバイアス低減で
  この床を締めるのが後続の最適化課題**（共通乱数・層化・hero 固定評価など）。
- **性能**: 1 スポットの 3-way 求解は既定（S=100k, 10 epoch）で ~15–30s。App フェーズでは S を下げるか
  Worker/WASM 化で短縮する（「計測して必要と分かってから」方針）。定性的レンジは S=16k でも安定。
