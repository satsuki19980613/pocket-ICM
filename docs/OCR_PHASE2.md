# OCR パイプライン設計（Phase 2 / packages/ocr）

版: 2026-09-02 / 状態: **画像非依存の純ロジック＝完成（56 tests green）＋較正ハーネス実証済み**、実画像較正＝進行中

## 位置づけ（SPEC §6.1）

**手入力が「正」、OCR はその手入力フォームを自動で埋めるプリフィル。** OCR がどれだけ失敗しても、
条件確認画面で全項目修正でき、手入力のみでリリースラインは常に維持される。したがって OCR の出力先は
`BoardForm`（＝ `packages/app` の手入力フォーム）であり、最終的に必ず `Confirm` 画面を経由する。

## 対象画面（さつき決定, 2026-09-02）

**入力は「リプレイ画面・プリフロップ終了フレーム」**（RTA 非実装の復習ツールのため、実運用の入力は
リプレイのスクショになる）。この画面は各席に**行動ラベル**（フォールド/レイズ/コール/オールイン/チェック）
を明示するので、状態復元をラベル駆動で堅牢にできる（ベット額推定より確実）。スタックは **BB表示/チップ
総額表示の両対応**（chips は左上ブラインド `bb_chips` で正規化）。実スクショで確認した事実:
- **Pot = 場に出た前チップ総和 + アンティ**（142820: `330+660+170×6 = 2010 = Pot`）。チェックサムは総額前提で一致。
- 左上 `SB/BB` `アンティ` は常にチップ建て。スタック/ベット/ポットのみ BB/チップを切替表示。
- **席の物理配置は人数ごとに異なる**（4人は TL/TR/BL/BC、6人は +TC/BR）。→ 人数別に layout プロファイルが要る。
- 解像度は提供分すべて 2730×1260（単一機種）。

## 中核の設計判断

### root spot 復元（最重要, spotReconstruction.ts）

solver は「全席 live・ブラインド投函済み・未開」の **root を全木で解く**
（`nwaySolver`: `T = stack + bet + antePaid`、`state !== 'empty'` の席のみ対象。誰が既にフォールド/
シューブしたかは結果画面のノード選択で扱う）。よって OCR は途中状態のスクショから root を逆算する:

```
putIn_i      = folded ? 席のブラインド義務 : screenBet_i     // フォールド済みのデッド分を含む
fullBehind_i = screenStack_i + putIn_i                       // ante は solver が別途加算
rootStack_i  = fullBehind_i - blindOb_i
rootBet_i    = blindOb_i    (SB=sb, BB=bb, それ以外 0)、state = 'live'
```

`T = rootStack + rootBet + antePaid = screenStack + putIn + ante` が配布時の全持ち込みに一致する
（シューブ済み席 `screenStack=0, screenBet=全額` も、フォールド済み席も正しく root に戻る）。

### 対象外検出（§6.5, 2-7）— 行動ラベル駆動

push/fold Nash はフォールドとオールインしか持たない。有効な終了フレームのラベルは
`fold / allin / call（場にオールインがある場合のみ）/ check（BB のみ）`。したがって:
- **raise**（非オールインのオープン/ミニレイズ/3bet）→ 対象外。
- **call だが場にオールインが無い**（リンプ/非オールインへのコール）→ 対象外。
- **hero が BB でオールイン・レイズ・コールのいずれも無い** → ウォーク（no decision）として弾く。

ラベル駆動により「**オールインをカバーしてコールした席**」を正しく push/fold 有効と判定できる
（ベット額だけでは非オールイン自発コミットと誤判定してしまう）。この席も root では full behind に戻る。

### ポット・チェックサム（§6.3, 2-8）

`Σ(各席の拠出) + アンティ寄与 ≒ ポット`。不一致なら `pot` と各 `bet` の信頼度を下げ、条件確認画面で強調。
**注意（較正対象）**: OCR の `pot` 読み取りが「中央ポットのみ」か「場に出た総額」かは実機表示に依存。
現状は総額前提の理論値で突き合わせ、tol は golden dataset で調整する。

### テンプレートマッチ（2-3/2-5）

描画フォント・カードデザインが固定なので学習器不要。**NCC**（輝度のオフセット・スケールに不変）で
装飾品や軽い明度差に頑健。候補は各テンプレサイズへ双一次リサイズしてから相関を取る。

## accuracy 検証の知見（AI 目視 vs OCR, さつき指示の照合規律）

- **カード角の NCC マッチは、同一画素では 7/7・score 1.000**（配線・アルゴリズムは正しい）。
- **固定分数座標のまま独立キャプチャに転用すると 1/4 に低下**（ハンド一覧は行がスクロールし、カード内での
  サンプル y が数十 px ずれると角の内容が別カードのテンプレに近づく。9c→3h, Js→9c の「1つズレ混同」）。
- **結論: カード認識は「白い札の矩形を検出→正規化→角を切る」が必須**（固定座標は不可）。プレイ画面は席位置が
  固定なのでカード領域も安定するが、テンプレ生成元のハンド一覧はスクロールするため検出ベースにする。
- **"10" は "10"（2文字）で描画**される（T へのマッピングと、10 用の幅広テンプレが要る）。

### 白札検出＋正規化で再検証（src/detect.ts）

`findCardRects`（明度マスク→連結成分→アスペクト/面積/充填率フィルタ, 純ロジック 5 tests）で白札を検出し、
各カードの左上角を**カード矩形基準で正規化**して切り出す方式に変更。144211 の数字カードでテンプレを作り、
**独立キャプチャ 144216 で照合**した結果:
- 照合スコアが **0.47〜0.66 → 0.96〜0.99** に改善（アライメント問題は解消）。**ランク認識はほぼ確定**。
- 完全一致は 4/6。残りは**スート誤り**（`4♥→4♣`, `4♦→4♣`, margin 0.005〜0.015 と極小）。グレースケールの角では
  同ランク別スートがほぼ同点になる。
- **絵札（J/Q/K）は顔絵が白領域を分断して未検出**（数字・A・"10" は検出成功）。グリッド補間 or 角限定検出で対応予定。

### 決定的発見: 4 色デッキ ＋ ランク/スート分離（検証済み）

accuracy 検証（AI 目視 vs OCR）で、このゲームは **4 色デッキ**と判明: **♠=黒, ♥=赤, ♦=青, ♣=緑**
（実測平均色 ♥(215,55,63)/♦(41,90,238)/♣(33,134,76)/♠(16,16,16)）。よってスートは**インク色で決定的に分類**できる。

**確定した認識アーキテクチャ（src/color.ts, src/detect.ts）:**
- **スート = 4 色分類**（`classifySuitColor`/`recognizeSuit`, 純ロジック 5 tests）。実画像 **17/17**。
- **ランク = グレースケール NCC**（検出正規化した角に対して）。スート別テンプレは不要 → **13 rank テンプレのみ**。
- **検証（独立キャプチャ 144211→144216）**: rank テンプレのある 12 枚で **rank 12/12・suit 12/12・フルカード 12/12**
  （rankScore 0.96〜0.998）。固定座標の 1/4 から完全解決。テンプレ外は rank 2/7/10 が未登録なだけ。

**絵札検出（解決）**: 顔絵が白枠を分断する問題は、明度マスクに**モルフォロジー・クロージング**
（`close`, dilate→erode, 半径 1）を掛けて枠の断裂を橋渡しして解消。144211 で **21/21 検出**（絵札含む）。

**色対応 recognizeCard（統合済み, src/cards.ts）**: `recognizeCardColor`/`recognizeHeroHandColor`。
ランク=グレースケール NCC（テンプレ label はランク "2".."9","10","J","Q","K","A"、"10"→core 'T'）、
スート=`recognizeSuit`（顔絵を避け左上のランク文字だけを色サンプル: 角 0.42×0.30）。合成 3 tests。
**独立キャプチャ 144216 で検証: rank 16/16・suit 16/16・フルカード 16/16（絵札 J 含む）**。
※検証中に AI の目視ラベル誤り（J♥ を J♦ と誤記）を OCR 出力との照合が捕捉 → 照合規律の双方向の価値。

**残（カード認識）**: 13 rank テンプレの完全収集（2/7/10 ほか。初回セットアップ＝ハンド一覧スクショから、
検出→正規化して rank ごとに1枚）。プレイ画面では hero 2 枚は固定座標なので検出不要（座標較正のみ）。

## 数字 OCR accuracy 検証（chips・6人で実証, 2026-09-02, 5 並列エージェント分担）

カード認識と同型の **白マスク→連結成分→グレースケール NCC** で数字を読む。

- **白マスク**（`digitsCore.whiteMask`）: 4 色デッキで数字は白なので `min(R,G,B)` が高く低彩度の画素だけを前景化 → 赤蝶/青キラキラ/緑等の装飾色を除去（スート色分類と同じ発想）。
- **連結成分ラベリング**（`glyphRects`）: `0`/`8` の中空を縦投影で割らず、背景ノイズは面積で除去。**背の低い成分（コンマ/小数点/線飾り）を落として数字だけ整列**（`digitRects`）→ `parseAmount`。数字は**中央寄せ**でコンマが隙間を埋めるため桁間ギャップは常に小（装飾は大ギャップで離れるが、gap クラスタリングは先頭/末尾装飾の取り込みで不安定だったため不採用。領域を数字中央にタイト較正して除く方針）。
- **テンプレは 0-9 の 10 種のみ**（`local-fixtures/digits.json`, .gitignore）。複数フィールドから収集（"5" は 19,453 から）。
- dev ツール（scripts/, 依存ゼロ）: `digitsCore.ts`（共有コア）/ `digitsTool.ts`（build/recog/multi）/ `verifyFrame.ts`（6 人領域をベイク, 画像＋正解で照合）/ `tuneField.ts`（フィールド別に領域 nudge×閾値をグリッド探索）。

**結果: chips・6人・CLEAN フレーム 11 枚で 85/88（96.6%）。** 誤り 3 件は全て**物理的な遮蔽/発光**（fold タグが桁上端を削る tcstk、手番のシアン発光枠が数値を壊す brstk）で、**信頼度 < 0.80 でフラグ**（正読は全て ≥0.80、発光失敗は 0.25）。閾値 ~0.80 が分離線 → プリフィル＋確認画面で誤フィールドだけを強調できる。

**決定的知見**: tlstk/bbstk 等の系統失敗（`9→8`, `6→5`, 先頭桁欠け）は透かしではなく**プロファイル全体の僅かな右下 offset**。`tuneField` で全席が `dx≈-0.004` を最適とした。席別に offset＋タイト化して解決。BB 席の楕円プレート両端の宝石飾りは `minCh=168` で除去。

**残（数字 OCR）**:
1. **BB 建て（小数）モード未対応**: 末尾の " BB" 単位が "88" に誤読され、小数点処理も無い（142955/143002/142936/142947/103554 等）。BB 建て専用パス（単位除去＋小数点対応）が要る。
2. **人数別 layout プロファイル**: 結果画面はフォールド者が **absent（完全非表示）**、席が動的再配置。2-5 人は別プロファイル。
3. ベット領域は 2 つのみベイク（全席分が要る）。
4. src への移植（現 `src/digits.ts` は旧・縦投影版。実効は `digitsCore` 方式）＋信頼度 ~0.80 閾値。
5. **対象外フレーム判別**: TRANSITIONAL（中央のカード配布アニメで pot 遮蔽）/ NONPREFLOP / ショーダウン・勝者アニメ（スタックが手札/WINNER/役ラベルに置換）/ 一時停止オーバーレイ を gate・占有検出で弾く。
