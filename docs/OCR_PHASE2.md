# OCR パイプライン設計 — アンカー・アーキテクチャ（packages/ocr）

版: 2026-09-08 / 状態: **純アンカー方式へ全面移行を決定（さつき）**。Phase 0 実証済み → Phase 1 仕様（本書）→ Phase 2 実装 → Phase 3 テスト＋無停止カットオーバー。

> 本書は 2026-09-02 の初期「固定座標プロファイル」設計を置き換える。固定座標は §D に**レガシー／カットオーバーまでのフォールバック**として残す。実証済みで不変な機構（root 復元・4 色カード・NCC・信頼度集約・ポット・チェックサム）は §C に継承。

## A. 位置づけ（SPEC §6.1・不変）

**手入力が「正」、OCR はその手入力フォームを自動で埋めるプリフィル。** OCR がどれだけ失敗しても、条件確認画面（`Confirm`）で全項目修正でき、手入力のみでリリースラインは常に維持される。OCR の出力先は `BoardForm`（`packages/app`）で、最終的に必ず `Confirm` を経由する。取り込み条件は **BB 表示のスクショのみ**（SPEC §5.2）。入力は主に**リプレイ画面・プリフロップ終了フレーム**。

## B. 目標アーキテクチャ：アンカー方式（解像度・アスペクト非依存）

### B0. なぜ全面移行するか（動機）

固定座標プロファイル（機種ごとに較正した割合矩形）は、較正した解像度・アスペクトから外れた画像で全席がズレて総崩れする。実データで判明した破綻例＝**1310×536 の実機由来フレーム**（`img.w>=2400` の二値分岐が iPhone プロファイルを誤選択し、Pot も stack も誤読 → アプリが棄却）。**ランドマーク（アンカー）からの相対読み**なら、アンカーが読める限りどの解像度でも成立する。Phase 0 の実証（§B10）で、アンカー機構が 2730/1792/1310 を横断し、固定座標で読めない 1310 を救えることを確認済み。

### B1. パイプライン全体（純アンカー）

```
入力画像(任意解像度/アスペクト, PNG/JPEG)
  → [B2] 拡大正規化フロントエンド（作業スケールへ正規化）
  → [B3] 席列挙（アバター＋黄色名＋テーブル楕円＋リング位相 → 占有席の集合）
  → [B7] 表示モード判定（stack が "BB" 終端か）→ chips なら ok:false（§5.2 ゲート）
  → 各占有席: [B4] 名前アンカー → 直上の "N.N BB" を BB 高さでスケールして読む（stack）
             [B6] D ボタン（金ディスク）→ 最近傍席 = ボタン
  → [B5] Pot アンカー（中央 "Pot :" → 右の "BB" までの数字）＋ ポット・チェックサム
  → 左上ヘッダ: SB/BB・アンティ（チップ建て固定表示。ラベル "SB/BB" "アンティ" にアンカー）
  → リング位相＋ボタン → ポジション導出（positionDerivation）
  → [C1] root spot 復元（+ B8 の pot 整合・ブラインド固定）
  → BoardState → BoardForm（+ lowConfidenceFields）
```

**設計原則**: 「構造から確定できる量は、脆い画素読みに依存させない」。ポジションはボタンから確定、ブラインド額はブラインド表記から確定、未オープン/レイズの別はポットから確定（§B5/B8）。読み取りはアンカー相対でスケール不変にする。

### B2. 拡大正規化フロントエンド（必須）

- 入力を作業解像度へ正規化してからアンカー処理する。Phase 0 で、1310 幅ネイティブでは stack の "N.N BB" グリフが ~13px でセグメント不能 → NaN。**≥1.5× 拡大**で 3/4 stack と D ディスクが復活。既存 `resampleRgba`（双一次）を利用。
- スケール決定: まず黄色名の高さ or "BB" グリフ高さから画面のグリフスケールを推定し、テンプレ基準スケール（digits.json のグリフ高）に合わせて正規化する。**アンカーで測ったスケールで正規化する**のが要点（固定倍率でなく内容駆動）。
- 過拡大は無駄＝上限を設ける。JPEG 由来のボケは拡大では回復しないので、極端劣化は「読めるアンカーだけ返し、残りは lowConfidence」で確認画面に回す（棄却より情報を残す）。

### B3. 席列挙（最重要・退行リスクの核）

Phase 0 の教訓: 「黄色 1 塊 = 1 席」は**弱すぎ**（バナー/HUD/レベル表記/D ディスクの黄色を拾って過剰、可読性ゲートで過少 → 6→5 の再発）。**色だけに依存しない占有モデル**を要件とする:

- 占有席の陽の条件（複数信号の合議）:
  1. **アバター**（テーブル外周に沿う顔絵領域）の存在、
  2. その**直下の黄色いプレイヤー名**（`detectYellowName`、実測 78/78）、
  3. 名前が**テーブル楕円の外周リング上**にある（中央の Pot/ボード帯・上部バナー・下部再生 UI を幾何で除外）、
  4. 名前直上に **"N.N BB" の stack** が取れる（任意・取れない席も占有はしうる＝在席は stack 読取と独立, [[ocr-bb-multidevice]] の b2153df 方針を継承）。
- **席数の上限は 6**。検出した名前群を**テーブル中心周りの角度でリング整列**し、6 スロット（TL/TC/TR/BR/BC/BL に相当する角度帯）へ割当てる。1 スロット複数候補は最尤 1 つ、スロット無候補は empty。**hero は最下段中央（BC）＝表向きカード＋金枠**で自明に特定。
- 受理ゲート: 検出席数が妥当（2〜6）・hero 在席・D ボタン在席（§B6）を満たすこと。過剰/過少を検出したら lowConfidence で人数を確認画面に上げる（MAIN の「検出人数」安全網と接続）。

### B4. スタック読み（名前 → 直上の BB アンカー）

- 実装済みの `bbAmount.readAmountBbAnchored` を土台にする（commit 5d5337e）。名前ボックス中心 `cx` を渡し、名前の**直上**の帯で "BB" 候補を列挙 → **直左に数字塊がある候補**かつ **`cx` に最も近い候補**を本命に選ぶ（ポジション BB バッジ＝左上、フェルト BB 表記＝左下 を除外。実測 40/40 分離）。
- **スケールは "B" の高さに固定**（BB 高さ≒数字高さ、実測 sd 0.022 の剛体）。カード絵柄のピップ等が帯に混入しても高さフィルタが狂わない。
- 桁認識は既存の digits NCC ＋小数点ゲート＋ scoreFloor（飾り片弾き, commit ac4bf78）を継承。発光弧は `trimArcBridge`/`stripEdgeBands` で除去（継承）。

### B5. Pot アンカー（中央 "Pot :" → 右の "BB"）＋ チェックサム

- 中央の「Pot :」は**一意・中央**。まず中央の Pot ピル（暗色角丸）を幾何＋"Pot" テキスト NCC で特定し、その右の "BB" までの数字を BB アンカーで読む（B4 と同型）。
- **ポット・チェックサム（さつき発案の整合則）**: 未オープン時の理論ポット `= playersLeft × ante + SB + BB`。
  - 読んだ pot が理論値と一致 → **未オープン確定**。各席の "ベット" はブラインドそのものと解釈し、脆いベット読みの誤り（例 SB 0.5→5）を**無視**する（§B8）。
  - 理論値より大きい → 誰かがレイズ/シューブ。差分と席のベットからレイザーを同定。
  - 大きく乖離 → pot と各 bet の信頼度を下げ確認画面で強調。
- これにより「SB のブラインド誤読が幻のレイズ扱いになって棄却」という実バグ（1310 で顕在）を、正常解像度では構造で防ぐ。

### B6. D ボタン → ポジション

- 金の "D" ディスクを**絶対位置で検出**（`button.ts`/`detect.ts` を拡張。しきい値は §B2 のスケールに相対化＝解像度不変に）。最近傍の席（名前）＝ボタン席。
- ボタン席からリングを時計回りに 1 周し `positionDerivation` でポジション（BU/SB/BB/UTG/HJ/CO）を導出。HU は SB=BTN。empty はスキップ（継承）。
- **SB/BB のブラインド額は導出ポジション＋ブラインド表記から確定**（読み取り不要）。

### B7. 表示モード判定（BB 表示のみ取り込み・SPEC §5.2）

- 各席 stack の末尾が "BB"（`stackEndsWithBb` の B ペア NCC）→ **bb**。数字で終わる → **chips**。
- chips と判定したら早期に `ok:false` ＋ `CHIPS_MODE_ISSUE`（既存文言）で棄却。**アンカー抽出は BB 表示のみを対象**とすればよく、chips の stack を正確に読む必要はない（chips は棄却のため検出だけでよい＝Phase 0 の「chips 1/24」は import 経路では非問題）。

### B8. root spot 復元（§C1 継承 ＋ 構造駆動の堅牢化）

§C1 の root 逆算を継承しつつ、**ブラインドは既知値に固定**し、**ポット整合（§B5）で未オープン/レイズを確定**してから逆算する。SB/BB の画面ベット読みが多少ズレても、未オープンが確定していれば `rootBet = blindOb` を使い、幻のレイズで棄却しない。

### B9. 合格基準（カットオーバー条件）＋ 無停止移行

**旧固定座標経路はカットオーバーまで残す。** 新アンカー経路を本番既定にするのは、以下を**全て満たしたときだけ**:

1. **既存の読み込み可能 27 枚**（iOS 2＋Android 25, 2〜6 人卓）で、BoardForm（playersLeft・heroPos・heroHand・blinds・ante・各ポジション stack）が **旧経路と同等以上**（現状 27/27 正）。
2. **表示モード判定**が旧同等（chips 110・対象外 BB 27 を正しく棄却）。
3. **1310×536 の劣化フレーム**が読める（pot 2.5＋主要 stack＋ポジション）。読めない残（例: ピンク台の白文字＝§B10 の別課題）は lowConfidence で確認画面に上げる。
4. `tsc` 緑・ocr ユニット緑・両機種 accuracy 無回帰。

満たすまでは**フォールバック運用**（既知解像度=固定座標で読み、失敗/未知解像度=アンカーで再挑戦）でもよい。純置換は基準達成後に固定座標を撤去して完了とする。**push/デプロイ禁止**（[[deploy-url]] ハザード）は全期間で厳守。

### B10. Phase 0 実証（本設計の経験的根拠, 2026-09-08）

本番非接続の試作リーダで実測（Sonnet サブエージェント＋指揮側 crop 目視）:
- **機構は解像度横断で健全**: 席が取れれば stack はほぼ本番精度＋誤読ほぼゼロ。Pot アンカー機能。
- **1310 劣化を救出**: pot 2.5 正読（固定座標は 12.9 誤読）、≥1.5× 拡大で 3/4 stack＋D ボタン復活。名前アンカーは ~10px まで頑健。
- **画質の床/課題**: (i) stack "N.N BB" は低解像度で要拡大（§B2 を必須要件化）、(ii) 白文字 on 色付きプレート（ピンク台 Chris 73.3）は `whiteMask` コントラスト限界＝アンカーと直交する別課題、(iii) D ディスクしきい値はスケール相対化が必要、(iv) 素朴な「黄色=席」は過剰/過少 → §B3 の合議モデル必須。
- **試作の弱点（＝要件化した理由）**: 素朴版は stack 50%・≥4 人で人数過少・chips 1/24。これらは §B2/B3/B7 の要件で解消する設計。

## C. 継承する実証済み機構（不変）

### C1. root spot 復元（spotReconstruction.ts）

solver は「全席 live・ブラインド投函済み・未開」の root を全木で解く（`T = stack + bet + antePaid`、`state!=='empty'` の席のみ）。OCR は途中状態から root を逆算:

```
putIn_i      = folded ? 席のブラインド義務 : screenBet_i
fullBehind_i = screenStack_i + putIn_i
rootStack_i  = fullBehind_i - blindOb_i
rootBet_i    = blindOb_i (SB=sb, BB=bb, 他 0)、state='live'
```

シューブ済み席（`screenStack=0,screenBet=全額`）もフォールド済み席も正しく root に戻る。NaN stack は席を落とさず仮値 0＋lowConfidence（b2153df 継承）。

### C2. 4 色デッキ・カード認識

**♠=黒 ♥=赤 ♦=青 ♣=緑**。スート=4 色分類（決定的, 実測 17/17）、ランク=グレースケール NCC（13 rank テンプレ）。白札検出→正規化→角切り（固定座標不可）。hero 2 枚は帯検出＋色認識（`recognizeHeroHandColor`）。"10" は 2 文字描画（core 'T'）。

### C3. NCC・信頼度・ポットチェックサム

NCC（輝度オフセット/スケール不変）で装飾に頑健。信頼度は閾値 ~0.80 で分離、低信頼は `lowConfidenceFields` で確認画面強調。ポットチェックサムは §B5 の整合則に発展。

### C4. cardState（active/folded）機種別指標

非 hero 席の active/folded は `FrameProfile.handActive`（Android=bright/0.06, iOS=strong/0.05）。アンカー方式でも席カード領域は名前アンカーから相対で取得して同判定を適用（ただし action はフォームに非伝播＝求解無影響, [[ocr-bb-multidevice]]）。

### C5. アクションマーク読み（★ 2026-09-10 さつき指示で C4 を置き換え）

**固定サイズの吹き出しプレート（フォールド/コール/レイズ/オールイン/チェック）を読んで action を確定する**
（`actionMark.ts` / `actionMarkZone.ts`、テンプレ `assets/action_marks.json`）。C4 のカード裏色による fold 判定は
**カード裏が着せ替え可能**という前提の破綻で使えない（淡色キャラ絵スキンの実機フレームで**全席が fold** と誤判定し、
降りた席のベットを読まない仕様のせいでブラインドまで 0 になった）。マークはゲーム側の UI で着せ替え対象外。

**実測に基づく設計根拠**
- マークは**行動した席の分だけ消えずに残る**（`Screenshot_20260902-114640.png` は 4 席同時に見える）。したがって
  マークが無い席は「まだ行動していない」＝ `none` と言い切れる。
- プレートは**語の長さに依らず固定サイズ**（2730×1260 で 0.054×0.042 フラクショナル）。
- 2 状態あり、形と大きさは同じで**明るさだけ**が違う: 能動＝鮮やかな紫地・白発光の枠・白文字、
  フォールド＝沈んだ紫地・灰の枠・灰文字（RGB ≈ 128〜176）。このせいで固定しきい値の白文字マスク
  （`actionTag.ts` の minCh 125〜150）では両方を同時に満たせない――これが従来「フォールドは扱わない」としていた理由。

**読み取り手順**
1. **帯**: アスペクト帯×席の静的グリッド（`MARK_GRID_2P16`、実測値を登録）を第一候補とする。
   席名アンカーは装飾テーマ卓で黄色装飾に重心を引かれて壊れる（薔薇テーマの BR で 0.06h ずれた）。
   未較正帯は従来の席名アンカー相対オフセットへ落とす（回帰ゼロ）。
2. **プレートの特定**: 上下の枠線が**横一直線**に走る性質を使う。各行の最長ランを測り、
   長さが**プレート実寸の 0.70〜1.40 倍**に入る行を枠線候補とし、上下間隔が縦横比 0.36 に最も近い
   ペアを採る。連結成分の最大値ではだめ（フォールドの枠線はマスク上で四隅が切れてリングにならず、
   最大成分が文字の一部になる）。帯幅比でなく実寸基準なので、帯を広げても判定は緩まない
   （テーマ差で席が内側へ 0.027 寄るのを吸収するため帯は 0.130×0.100）。
3. **二値化**: プレート内で **Otsu**。実測しきい値はフォールド 61〜73 / 能動 126〜137 と大きく違うが、
   Otsu が各インスタンスで自動に合わせるので**インク率が両クラスで揃う**（0.19〜0.39 / 0.20〜0.27）。
4. **NCC**: 5 語テンプレ（多例 21 枚、緑無地卓／薔薇装飾卓／iOS を混ぜる）。
5. **偽陽性ゲート 3 重**: インク率・NCC 信頼度・**語のクラスとプレート彩度の整合**。
   彩度は帯で見る（fold 25〜49 / 能動 68 以上）。単一しきい値だと hero 席の常設装飾（スタックの金枠、
   彩度 55〜62）が「fold より上だから能動」と解釈されて偽陽性になる（実測 30 件）。

**実測成績**（`scripts/evalActionMarks.ts`）: 正解ラベル付き 157 席・5 解像度・2 テーマで **157/157**、偽陽性 0。
end-to-end（`scripts/accuracy.ts`）で action 94/101 → **101/101**、bet 89/101 → 91/101。

**採用しなかった安全網**: 「hero が未行動なら行動順で hero より後ろの席も未行動」という不変量は
**使えない**。既存の仕様テスト（`pipeline.test.ts`）に「hero は none ラベルなのに hero より後ろの席が
コール/レイズ済み」の局面が意図的に入っており（オールインをカバーしてコールした席の判定等）、
この前提では本来棄却すべき raise/call を消してしまう。導入してテスト 3 件を壊し、撤去した。

**残課題**: hero(BC) 席のマーク位置は検証済みの実例が 0 例（178 枚中）。対応スポットでは
hero は手番＝マーク無しなので影響はないが、hero が既に行動したフレームを検知したいなら素材が必要。
チェック（ポストフロップのみ）は GT に実例が 0 例。


### C6. アンティによる人数の整合（★ 2026-09-11 さつき決定）

**スタック表示が無い席は空席として数え、アンティで人数の整合を取る**（`anteSeatCount.ts`）。
装飾テーマ卓の実機フレーム（`Screenshot_20260910-192316.png`）で、上中央の空席を装飾のせいで
占有と誤読した「幽霊席」が 6 人目になり、スタック 0 の BB として確認画面の手前
（`buildBoardState` の「スタックは正の数か」）で弾かれ、利用者はエラー画面に落ちていた。

**原理**: クラブマッチのアンティは**全員 0.25 BB**（さつき確定）。アンティは座っている人数ぶん
ポットに入るので `pot = 場のベット合計 + 人数 × 0.25`。場のベットは行動マーク（§C5）から決まる:
マークの無い席はブラインドだけ（SB 0.5 / BB 1 / 他 0）、レイズ/コール/オールインの席は読んだ額。
正解ラベル付き BB 表示 24 フレーム（オールイン/レイズ/コールを含む）で 24/24 一致。

**判定は割り算ではなく仮説の比較**: スタック未読の席を「全部本物」「全部空席」とした 2 通りで
席順からブラインド位置を決め、予想ポットを読んだポットと比べて近い方を採る（許容 0.15 BB・
2 仮説の差 0.1 BB 以上）。割り算で人数を出すと、チップ 1 枚の読み漏らしで狂う（同フレームは
BB の 1 BB を読み漏らしており、読んだチップで割ると 9 人になる）。決着しなければ何もしない
（＝従来どおり読めない席は本物として残し確認画面で注意色）。行動マーク付きの席と hero は落とさない。
**判定位置は `extractAnchored` の最後**: 下流の総チップ保存チェック（`chipConsistency`）が
ポットを人数から計算し直して上書きするので、読んだポットが残っているうちに判定する必要がある。

**同じ調査で直した付随の不具合**
1. **マークの無い席のベットはブラインド額で確定**（`spotReconstruction`）。読み漏らした BB の
   チップのせいで BB のスタックが 1 少なく復元されていた。読んだ額は facts に残し、ブラインドを
   超えるチップ（マークの読み落とし）の検出にはそちらを使う。
2. **総チップ 90,000 を超える BB はヘッダの誤読**（`resolveBlindChips` → null）。同フレームは
   ヘッダの「280/560」を SB 3 / BB 8,828,054 と読み、幽霊席が消えたことで走るようになった総チップ
   チェックが「クラブマッチではない」と誤棄却した。SB×2 の救済は BB が**欠測**のときだけ（同じ
   ヘッダが壊れているなら SB も信用できない）。公式表の最大 BB は 60,000 なので正しい読みは落ちない。
   BB 表示ではヘッダが解決できなくても SB/BB は 0.5/1 で確定。アンティの読みが 0.15〜0.35 BB を
   外れたら 0.25 に置き換える（読めたときは既存の値を変えない）。

**実測**: accuracy ハーネスで悪化ゼロ、アンティ 22/22・席の有無 132/132・人数/ポジション 15/15、
以前後退していたチップ表示フレーム 142903 も回復。Pixel フレームはエラー画面 → 確認画面
（5 人・全ポジション正解）。

**教訓（検証手順）**: Node の accuracy ハーネス / diagFrame は OCR パイプラインだけを通り、
アプリの確認画面前の組み立て（`boardStateToForm` → `buildBoardState`）を通らない。
**画面に到達するかは、ユーザー経路テスト（Playwright で本番同一ビルドを開き、Supabase を全面
モックしてファイル選択から確認画面まで操作）で確かめる**。


### C7. BB 表示の丸めとポット照合（★ 2026-09-11 さつき決定）

**ポーカーチェイスは BB 換算の値（スタック・ベット・ポット）を小数第 2 位で四捨五入し、小数第 1 位
まで表示する**（末尾の .0 は出さない: 「Pot : 3 BB」）。公式の記載はネット上に見つからなかったので、
同じ局面をチップ表示と BB 表示で撮った組（公式 Web 版を機種エミュレーションで撮影したもの＝
`accuracy.multidev.groundtruth.json`）から実測で確定した:
5,850 → 29.25 → **29.3** / 6,250 → 31.25 → **31.3** / 12,050 → 60.25 → **60.3**（x.25 が x.3 なので
偶数丸めではない）、Android 実機 2.75 → 2.8（切り捨てではない）・3.0455 → 3.0（切り上げではない）。
実装は `core/src/bbDisplay.ts`（`roundBbDisplay`・浮動小数の足し算誤差 1.2+0.15=1.3499… を吸収）。

**確認画面のポット欄**（`app/src/components/confirmPot.ts`）: 以前は計算値どうしを比べて常に「一致」、
しかも丸める前の 2.75 を出していた（実機 Pixel で「画面は 2.8 なのに」と指摘）。現在は
ゲームと同じ丸めで表示し、**スクショから読んだポットと本当に照合**する。確認画面の局面は
配られた時点（SB+BB+人数×アンティ）なので、オールイン/コール/レイズの席の上乗せ分
（ベット − その席のブラインド）を読み取り結果から足して画面と同じ条件にしてから比べる
（上乗せ無し＝丸めた値が完全一致、上乗せ有り＝その席数 ×0.05 まで許容）。

**そのために直した周辺**
- 読み取り結果（`readout.pot`）には**画面から読んだ値**を残す（`pipeline.ts` の `potAsRead`）。
  総チップ保存チェックが整合するとポットを計算値に置き換えるため、そのまま渡すと照合が
  「計算値と計算値」になる。計算に使う `state.pot` は従来どおり置き換え後の計算値。
- OCR 側のポット・チェックサム（`confidence.ts`）も、行動マークの無い席はブラインド額で数える
  （§C6 の root 逆算と同じ扱い）。BB の 1 BB チップを読み漏らしたフレームで「理論 1.75 vs 画面 2.8」
  の誤不一致になり、全席のベットが要確認の強調になっていた。同じ理由で、マークの無い席のベットは
  チップの読みが怪しくても要確認にしない（確定値なので）。


### C8. ヘッダの BB 読みとストラクチャー表の照合（★ 2026-09-11 さつき指摘）

**読んだ BB は登録済みのストラクチャー表と照合し、表の値で計算する**（既定方針）。これが
Pixel 実機フレームで働かず、BU の 29.8 が 29.3 のまま確認画面に出た（さつき指摘）。

**原因**: ヘッダの読み位置（`HEADER_BLINDS`）は標準比率 2.167 で較正した固定座標。Pixel
2424×1080 では数値部が右へ +0.030〜+0.036 ずれており、「SB/BB 280/560」の末尾が切れて「B/BB」を
巻き込み "3/88280/54"（SB 3 / BB 8,828,054）と読めた。表と照合できず `blindChips` が立たないため、
**総チップ保存チェック（1 席の読み違いを 90,000 との差で直す処理）まで止まっていた**。
本当は通常 lv4（280/560/140）で表に載っている（以前「表に無いレベル」と判断したのは誤読が前提）。

**対策**（`extractAnchored.readHeaderBlinds`・`blindLevels.isTableConsistentBlinds`）: まず従来位置で
読み、表と照合できればそれを使う（較正機は従来どおり）。できなければ横位置を近い順にずらして読み直し、
「BB が表のレベルにタイト一致し、SB がちょうど半分」になる最初の読みを採る。表との照合そのものを
読みの正しさの判定に使うので、切れた数字や「BB」の文字を巻き込んだ読みは自然に落ちる。
ずらした量はアンティの読み位置にも使う（真下の枠で左端が揃う）。

**結果**: Pixel フレームで表 lv4 と照合 → 総チップ保存チェックが「調整」で働き、最低信頼の BU に
差 0.46 BB を足して 29.3 → 29.8（画面と同じ値・補正した席は確認画面で強調）。accuracy ハーネスは
デプロイ済み版と全項目同一（回帰ゼロ）。
