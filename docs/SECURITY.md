# セキュリティの考え方と運用手順

2026-09-11 のセキュリティレビュー（さつき依頼「個人の情報を格納するので安全性を保障したい」）で
見つかった穴を塞いだときの記録。**守りの仕組み・本番への反映手順・さつきさんがダッシュボードで行う操作・
確かめ方**をまとめる。コードの詳細はそれぞれのファイルのコメントにある。

## 守りの仕組み（誰が何を見られるか）

| データ | 見られる人 | 書ける人 |
|---|---|---|
| プロフィール（ユーザー名・表示名・アイコン） | メンバー全員 | 本人（ユーザー名・管理者フラグは変えられない） |
| アバターの枠の色（`frame_color`） | メンバー全員 | 本人（6色から選択。特別枠 `special` は管理者の付与が無いと選べない） |
| 特別枠・バッジ（`special_frame` / `badge`） | メンバー全員 | 管理者のみ（SQL Editor での直接 update） |
| 自分の計算記録 | 本人（公開したものはメンバー全員） | 本人 |
| 投稿・コメント・♡・ランキング | メンバー全員 | 本人 |
| スレッド画像・アイコンの画像ファイル | メンバー全員（期限付きの署名 URL でのみ） | 本人のフォルダだけ |
| スクショ（解析元画像）・読み取りログ | 本人と管理者 | 本人 |
| 全員の計算記録（非公開を含む・診断ログ） | 管理者（専用の関数 `admin_*` からだけ。`results` の閲覧ポリシー自体は「本人か公開」のまま） | — |
| アプリのエラー記録（`client_errors`） | 管理者 | 本人（送るだけ。自分でも読めない・直せない・消せない） |
| 登録上限・招待キー | 管理者 | サーバ（Edge Function）だけ |

- **メンバー** = 招待キーで登録した人（`profiles` 行を持つ人）。判定は `public.is_member()`。
  Supabase Auth に直接アカウントを作れても、メンバーでなければ何も読めず、何も書けない。
- **未ログイン** の人は何も読めない（全ポリシーが `to authenticated` ＋メンバー条件）。
- パスワードは Supabase Auth がハッシュで保存し、アプリは持たない。本名・メールアドレスは持たない
  （識別子は `ユーザー名@users.pocket-icm.app` という架空のアドレス）。
- 何でもできる鍵（service_role）は Edge Function の中だけ。リポジトリにもフロントにも置かない。
- 画像の参照（`image_url` / `avatar_url`）は「このアプリの Storage の、本人フォルダの画像」の形しか
  DB に入らない（CHECK 制約）。表示側でも同じ形を検証してから署名 URL に替える（`storageUrls.ts`）。
- ページには CSP などのセキュリティヘッダーを付ける（`packages/app/public/_headers`）。スクリプトは
  このアプリ自身のファイルだけ、画像・通信はこのアプリと Supabase だけ、他サイトへの埋め込み禁止。
- アカウント削除では、DB の連鎖削除に加えて Storage のファイル本体（スクショ・スレッド画像・アイコン）も
  消す。消せなかったらアカウントは消さずにエラーを返す（`delete-account`）。
- どこからも参照されなくなった画像ファイルは、週1の `purge-images` が回収する（24時間以上前のものだけ）。
  `purge-images` は利用者が書ける `images` 行の値（置き場所・大きさ・日時）を信じず、持ち主のスクショフォルダに
  実在するファイルだけを、Storage が記録した実物の大きさ・作成時刻で判断して消す。
  総量上限（700MB）を超えたときに消すのは「公平な取り分（上限 ÷ 人数）を超えて使っている人」の非保護スクショだけ
  （`_shared/purgePlan.ts`）。1人が大量に上げても（保護にしても）、取り分以内の人のスクショは消えない。
  保護スクショだけで上限以上のときは何も消さず、`warn_protected_over` / `warn_over_limit` で知らせる。
- 新規登録は「招待キーの下見（消費しない）→ Auth アカウント作成 → プロフィール作成と招待キーの消費を
  1トランザクション（`register_member`）」の順。キーが無効ならアカウントを作らない（ユーザー名の有無も明かさない）。
  途中で失敗しても「招待キーを使っていないメンバー」は残らない。
- 投稿・コメント・画像記録の作成日時はサーバの時刻。更新で変えられるのは本文・画像（投稿）と保持方針（画像記録）だけで、
  種別・紐づく結果・所属スレッド・置き場所・大きさはトリガで固定。「（編集済み）」の目印（updated_at）も
  本文・画像が変わったときだけサーバが付ける。記録・読み取りログから参照できるのは本人の画像・結果だけ。
- 新規登録の旧経路（0008 適用前の手順）に落ちるのは `check_invite` が存在しないときだけ。一時的なエラーでは
  旧経路に落とさず 503 を返す。
- 画像の署名 URL は1時間。表示中の画像は4分ごとに見直し、期限が近ければ取り直す。取り直しに失敗しても
  表示中の署名 URL を使い続ける（公開 URL に替えない）。
- 他のメンバーが投稿したデータの形が壊れていても、その1件を表示しないだけで画面全体は落ちない
  （`feed.ts` の形の検証＋画面ごと・投稿カードごとの `ErrorBoundary`）。
- CSP の `connect-src` に `data:` を入れているのは必須。Vite が小さな `?url` アセット（求解テーブルの `*.meta.json`）を
  `data:` URL としてワーカーに埋め込み、ワーカーがそれを fetch するため（塞ぐと HU の計算が失敗し、3〜6人は黙って
  モンテカルロに落ちて数値が変わる）。`data:` はページ内の値を読むだけで外へは何も送らない。

- 画像参照の CHECK 制約はこの Supabase プロジェクト（`bpxrbxnylgedjhvhfsvk`）の URL に固定している。
  プロジェクトを移すときは `0008_security.sql` の該当箇所と `_headers` の CSP を書き換える。

### 残っているリスク（承知の上で残しているもの）

- **容量の使い切り（可用性）**: メンバーが自分のフォルダに大量の画像を上げると、無料枠（Storage 1GB）を
  使い切れる（上げられなくなる）。週1の削除は取り分（上限 ÷ 人数）を超えて使っている人の分からだけなので、
  取り分以内の人の画像は消えない。ただし取り分を超えて使っている人は、合計が上限に収まるまで古い非保護スクショ
  （どのみち90日で期限切れになるもの）が消えることがある。保護スクショは自動では消さない。
  招待制で相手が分かっている前提で、利用者ごとの容量上限は設けていない。`purge-images` の `warn_over_limit` /
  `warn_protected_over` が立ったら管理者が確認する。
- **ランキングの値**: Slumbot の成績は端末からの申告（1ハンド ±200bb の範囲は DB が弾く）なので、正しさは保証しない。

## 本番への反映手順（この順番で）

1. **アプリをデプロイ**（master へ push → Cloudflare が自動デプロイ）。新しいアプリは画像を署名 URL で
   出す。SQL 適用前は署名できないので、自動で従来の公開 URL にフォールバックする（表示は変わらない）。
2. **SQL を適用**: Supabase ダッシュボード → SQL Editor に `supabase/migrations/0008_security.sql` を
   丸ごと貼り付けて実行。何度実行しても壊れない。形の合わない古い画像参照があれば NOTICE が出る
   （適用は止まらない）。**1 より先に実行すると、古いアプリで画像が一時的に出なくなる。**
3. **Edge Function をデプロイ**: `npx supabase functions deploy signup delete-account purge-images`
   （CLI にログイン済みであること）。SQL より先でも壊れない（signup は `check_invite` が無ければ
   従来どおりの判定になる）。

### 診断ログ（0009, 2026-09-11 追加）

- `supabase/migrations/0009_diagnostics.sql` を SQL Editor で1回実行する（冪等）。アプリのデプロイとは順不同
  （SQL が無い間は診断ログ画面が「サーバの準備がまだです」になり、エラーの送信は黙って失敗するだけ）。
- 全員の計算記録・OCR の読み取り・アプリのエラーは、管理者専用の関数 `admin_diag_summary` / `admin_list_runs` /
  `admin_list_ocr_reads` / `admin_list_client_errors` からだけ読める。関数の中で `is_admin` を確かめ、
  管理者以外（メンバー・招待外・未ログイン・service_role）は 42501 で拒否する。
- `client_errors` はメンバー本人の行を書けるだけ（読めるのは管理者だけ・更新／削除は誰もできない）。
  1人1時間30件まで・90日より古い行は挿入のついでに消える。
- 管理画面のプログラム（`adminScreens-*.js`）は PWA の precache から外しているので、管理者以外の端末には
  ダウンロードされない。

### アバターの枠・バッジ（0012, 2026-09-16 追加）

- `supabase/migrations/0012_avatar_frames.sql` を SQL Editor で1回実行する（冪等）。
- `profiles.frame_color` は本人が6色（steel/yellow/cyan/red/white/purple）から自由に選べる。
  `special` は特別枠が付与されている（`special_frame` が入っている）ときだけ選べる
  （`protect_profile_privileged` トリガが、付与なしでの `special` 指定を元の色に戻す）。
- `profiles.special_frame`（色指定の16進 or `prism`）・`profiles.badge`（今は `crab` のみ）は
  管理者が SQL Editor で直接 update するだけ（付与 UI は今回作らない・付与手順は
  0012 のファイル末尾コメント参照）。本人からは一切書き換えられない。
- 特別枠を取り消す（`special_frame` を null に戻す）と、`frame_color` が `special` のままの人も
  自動で `steel` に戻る（同じトリガが面倒を見る）。

## さつきさんがダッシュボードで行う操作（コードでは変えられない設定）

- **Authentication の設定で「Allow new users to sign up（新規ユーザーの登録を許可）」をオフ**。
  招待キーでの登録は Edge Function がサーバ権限で作るので、オフにしても今までどおり動く。
  メンバー条件があるので万一オンに戻っても中身は見えないが、見知らぬアカウントが作られること自体を防ぐ。
- **Email プロバイダの最小パスワード長を 8 にする**（登録時は Edge Function が 8 文字以上を強制しているが、
  設定画面からのパスワード変更は Supabase Auth の設定値で判定されるため）。

## 確かめ方

- 新規登録のスイッチ（読み取り専用・公開の設定窓口）:
  `GET https://<project>.supabase.co/auth/v1/settings`（ヘッダ `apikey: <公開キー>`）の
  `disable_signup` が `true` なら閉じている。
- 招待を通らずに作られたアカウントが無いか（SQL Editor）:

  ```sql
  select u.email, u.created_at
  from auth.users u
  where not exists (select 1 from public.profiles p where p.id = u.id);
  ```

- 管理者が誰か（SQL Editor）: `select handle, created_at from public.profiles where is_admin;`
