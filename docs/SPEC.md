## 0. プロダクト概要

- 招待制の**閉じたクラブ内 ICM 学習ツール兼 SNS**（利用者は最大25人）。
- コア体験＝**トーナメントのスクショ → OCR → push/fold の最適解を即時表示**。復習を仲間と共有できる。
- ソルバーは**完全に端末内**で動く（HU/3人/4人＝事前計算テーブル、5-6人＝直接求解／NN 蒸留）。
  サーバは「アカウントと共有データ（スレッド・記録・画像）」のみを担う。
- **絶対条件: いかなる場合も課金が発生しない**（§7）。

## 1. 用語

| 用語 | 意味 |
|---|---|
| スポット | 1つのハンド状況（人数・スタック・自分の手・ポジション等） |
| push / fold | オールイン or フォールドの二択（AOF: All-in or Fold）。※「押し引き」表記は使わない |
| ノード | Action tree 上の1つの決定点（各ポジション×各前段状態） |
| PU / CA / OC | Push / Call / Over-call（前段状態で種別が変わる） |

| 結果投稿 / 通常投稿 | スレッドの2種別。結果投稿＝計算結果の公開、通常投稿＝文字のみ／文字＋画像（§5.1） |
| 招待キー | アカウント作成に必要な**1回限りの使い捨てコード**（§3） |

## 2. アカウント / 認証

- **サインアップ**: 表示名・ユーザー名（@handle）・パスワード＋**招待キー**を入力。
  - 招待キーが有効で、かつ登録人数が上限未満のときだけ作成できる（判定は必ずサーバ側）。
- **ログイン / ログアウト**。パスワード変更（設定画面）。
- **プロフィール画像**（設定画面で選択）。
- **アカウント削除**（設定画面。自分の記録・スレッド・コメント・画像も連鎖削除）。
- 対応画面: `auth`（ログイン / 作成）, `profile`（設定）。

## 3. 招待キー（1人ずつ・使い捨て）

さつきが**1人ずつ**招待する。招待のたびに**毎回異なるキーを1つ発行**し、相手に渡す。

### 3.1 キーの性質（シンプル＆安全）
- **1回限り**: 1つのキーで作れるアカウントは1つだけ。使われた瞬間に無効化。
- **推測不可**: 暗号学的乱数で生成。曖昧文字（0/O/1/I/l）を除いた英数字。
  - 形式: `POCKET-XXXX-XXXX`（読みやすい区切り。LINE等で送りやすい）。将来、桁数は容易に増やせる。
- **有効期限**: 既定 **7日**（未使用のまま期限切れ→自動失効）。期限は管理画面で変更可。
- **保存はハッシュのみ**: DB には生キーを保存せず**ハッシュ**を保存。DB が漏れてもキーは使えない。
  - 生キーは**発行時に一度だけ**画面表示（コピー可）。以後は本人も見られない（再発行で対応）。
- **状態**: 未使用 / 使用済み / 取消 / 期限切れ。

### 3.2 サインアップ時のサーバ側検証（Edge Function）
1. キーのハッシュが「未使用・未失効・未取消」で存在するか。
2. 現アカウント数 < 上限か。
3. 両方満たせばアカウント作成 → キーを「使用済み（used_by/used_at）」に更新（原子的）。
4. どれか満たさなければ拒否（理由別メッセージ: 無効キー / 期限切れ / 満席）。

## 4. 管理画面（さつき専用）

さつきのアカウントだけがアクセスできる画面。画面 ID: `admin`。

### 4.1 入り方（安全策）
- 新しいパスワードは作らない。**さつきの通常アカウントに「管理者」フラグ（`is_admin`）を1つ付与**する方式。
- ログイン中に管理者フラグがあるときだけ管理画面が出る。他ユーザーには存在ごと見えない。
- 管理者フラグの付与は**初期設定時に1回だけ**（DB直・開発者作業）。アプリ上に昇格機能は作らない。

### 4.2 できること
- **登録状況**: 現在の登録人数 `X / 上限`。
- **アカウント上限の変更**: 数値入力（初期値25）。サーバ側で強制。
- **招待キーの発行**: ボタン1つ → 使い捨てキーを生成し**一度だけ表示**（コピー可）。
- **招待キー一覧**: マスク表示のキー・状態・使った人・発行日・有効期限。
- **未使用キーの取消**（revoke）。
- **【v3 追加】ストレージ使用量**: 画像の総量（成功／失敗の内訳）と上限までの余裕を表示（§7.2 の運用監視）。
- **【v3 追加】OCR 失敗の件数**: 直近の OCR 失敗・低信頼の件数（詳細解析はローカルスクリプトで行う・§12.3）。

### 4.3 サーバ側の保証
- 上限変更・キー発行/取消は**管理者フラグを持つ本人のみ**（RLS＋Edge Function で二重に強制）。
- クライアント判定に依存しない（改竄不能）。

## 5. 画面仕様（モック準拠）

各項目末尾の `code` はモックの画面 ID（`data-go`）。

### 5.1 ホーム `home` / スレッド `thread` / 他人の公開 `userpub`（SNS 面）

#### 5.1.1 フィード
- 新しい順に**スレッド**が並ぶ。スレッドは2種別:
  - **結果投稿**: 計算結果を公開したもの。結果カード（手札/判定/bb/レンジ%/EV）＋一言コメント。
  - **通常投稿（v3 新設）**: 計算結果を伴わない投稿。**本文のみ**、または**本文＋画像1枚**。
- どちらも表示要素は共通（投稿者・相対時刻・本文・返信数・♡）。結果投稿だけが結果カードを持つ。
- 返信・♡・自分の投稿の編集・削除は**両種別で同じ**に動く。

#### 5.1.2 通常投稿の作成（v3 新設）
- 入口は**ホームの FAB（＋）**。押すと投稿コンポーザ（モーダル）が開く。
  - v2 まで FAB は ICM 計算へ飛んでいたが、**計算は ICM タブから**に一本化する。
- 入力: 本文（最大2000字）＋画像1枚（任意, PNG/JPEG/WebP・5MB以下）。
- **本文・画像の少なくとも一方**が必要（両方空なら送信不可）。
- 投稿すると自分の通常投稿としてフィード先頭に出る。タップでスレッド詳細。
- 自分の通常投稿は**本文の編集**と**削除**ができる（削除は返信ごと消える）。

#### 5.1.3 スレッド詳細 `thread`
- 見出し（結果投稿＝結果カード / 通常投稿＝本文・画像）＋♡＋返信一覧＋返信コンポーザ。
- 返信は任意アカウントが自由に投稿でき、**画像添付可**（従来どおり）。
- 自分のコメントの編集・削除。
- 他人のプロフ画像タップ → その人の公開一覧 `userpub`（読み取り専用）。
- 自分のプロフ画像タップ → 記録タブ `records`。

### 5.2 ICM 計算入力 `icm` → `confirm` / `error`

- **写真選択ボタンを最上位**に配置、その下に「読み取れる条件」チェックリスト（§5.2.1）。
- **手入力はサブ**: 「手入力する」ボタン → **手入力モーダル**（現行フォームをモーダル化）。
- 写真選択後 → **条件確認/修正** `confirm`（読み取り内容表示・各項目「修正」・低信頼強調）。
- 対象外/読取失敗 → **エラー** `error`（欠け項目・「別の写真」/「読めた分を手入力」）。
- **計算中は写真選択・手入力とも無効**（§5.7 の同時1件制約）。

#### 5.2.1 読み取れる条件（★v3: 実装と一字一句そろえる）

チェックリストの文言は**実際に弾いている条件と一致させる**。以下が正であり、UI（`icm` と `error` の
両方に同じリストを出す）と実装（かっこ内が判定箇所）はこの表から外れてはならない。

| # | 条件 | 実装での判定 |
|---|---|---|
| 1 | **プリフロップの画面**（フロップ以降・ストリート表示が読めないものは不可） | `streetGate`（`preflop` 以外と `unknown` を棄却） |
| 2 | **スタックが BB 表示**（例 `20.2 BB`）。チップ総額表示（例 `19,453`）は不可 | `reads.displayMode !== 'bb'` で棄却（`prefill.ts` / `CHIPS_MODE_ISSUE`） |
| 3 | **オールインとフォールドだけで進んだ場面**。レイズ・ミニレイズ・3bet・リンプ（非オールインへのコール）が入った局面は不可 | `detectOutOfScope`（raise / 非オールイン call を棄却） |
| 4 | **自分の判断がある場面**。全員フォールドで BB に手番が回ったウォークは不可 | `detectOutOfScope`（hero=BB かつ未レイズを棄却） |
| 6 | **切り抜いていない全画面のスクショ** | アンカー抽出（`extractAnchored`）が画面全体のランドマークを前提とする |
| 7 | **Sit & Go の局面**。ブラインド構造が公式表（通常／ゆっくり／もっとゆっくり）にあること | ブラインドが公式表にタイト一致すれば受理。**一致せず、かつ**場のチップ総量が 6人×15,000＝90,000 と 15% 以上食い違うときだけ棄却（`chipConsistency` の `not-club-skip` → `pipeline.ts`） |

- 補足表示（チェックリスト外の小文字注記）: 対応形式は PNG / JPEG / WebP。**画像の解析は端末内で完結**する
  （解析後の保存については §7.2・§12 で説明し、設定画面からも参照できるようにする）。
- 条件 3・4 は v2 のチェックリストに無かったが**実装は弾いている**。v3 で明示する（これが今回の
  「表記を実装に合わせる」の中身）。
- 旧・条件5「2〜6人の局面」は **2026-09-10 にチェックリストから外した**（さつき指示）。
  ポーカーチェイス自体が 6-max なので利用者に伝える意味が無い。実装側の `MAX_PLAYERS = 6` 超で
  `error` にする保険は**そのまま残す**（7人以上の盤面が届いても解かない）。
- 条件 7 は **2026-09-10 追加**（さつき決定）。ソルバーはクラブマッチの実払い（+5/+3/+2/+1/0/-1・§2.1）を
  固定で使うため、他モードのスクショをそのまま解くと**間違った EV を警告なしに返す**。
  判定は 2 段構えで、**まずブラインド構造を見る**: 公式表（通常16／ゆっくり32／もっとゆっくり59 レベル）に
  タイト一致すればクラブマッチとみなして受理する（さつき指示 2026-09-10:「登録されているストラクチャーに
  当てはまっているものは弾かない」）。表に無い構造のときだけ、総チップ 90,000 との乖離で判定する。
  したがって実際に棄却されるのは**未知のブラインド構造 かつ 総チップも合わない**という二重に外れた
  フレームに限られる。現行のフィクスチャではこの条件に当たるものは無い（安全網としての位置づけ）。
  しきい値 15% の根拠（実測・GT 全 BB 表示フレーム）: 正しく保存しているフレームの乖離は 0.1% 未満、
  対象外（レイズ/リンプで場に追加ベットがある）フレームでも最大 2.5%。一方、他モードの実機フレームは
  33%（6-max・開始 20,000）・56%（HU・開始 20,000）と桁違いに離れる。
  なお **BB 表示は 0.1 刻みに四捨五入**されており、その残差は席数に比例して合計に積み上がる
  （実測 -0.10〜+0.10bb）。これを誤読と誤判定しないよう、保存則の許容差は席数に比例させる（§6.3）。

#### 5.2.2 条件確認 `confirm`
- 読み取った内容（ブラインド・ハンド・ヒーロー・人数・ポット検算・各席スタック/ベット）を表示。
- OCR 低信頼フィールドは CHECK バッジで強調。総チップ保存チェックで補正した席も強調。
- 写真経由のときは**検出人数**をその場で直せる（安全網・現行どおり）。
- 「この内容で計算する」で計算開始（§5.7）。

#### 5.2.3 元画像モーダル＝**画像 × OCR 出力の照合ビュー**（★v3 新設）
「元画像を確認」で開くモーダルは、**元画像とその画像から OCR が出力した値を同時に**表示する。
利用者が目で見比べて誤読を見つけられるようにするのが目的。

- **開ける場所は2つ**（両方で同じコンポーネント・同じ内容）:
  1. **条件確認画面** `confirm` の「🖼 元画像を確認」
  2. **手入力（修正）モーダル** の「🖼 元画像を確認」
  - さらに写真由来の**エラー画面** `error` からも開ける（何が読めて何が読めなかったかを見せるため）。
- **上段: 元画像**。既定は全体表示、タップで原寸⇔全体を切り替え（現行 ImageModal の挙動を維持）。
- **下段: OCR 出力**。以下を席ごとに1行で並べる（画像の並び＝時計回りの席順を保つ）。

| 列 | 内容 |
|---|---|
| ポジション | 導出後のポジション（UTG/HJ/CO/BTN/SB/BB）。導出前・導出失敗時は席 ID |
| 目印 | hero / D（ボタン）のバッジ |
| 状態 | 配牌あり（occupied）/ 空席（empty） |
| アクション | fold / call / raise / allin / check / なし |
| スタック | BB 換算の数値 |
| ベット | BB 換算の数値（0 は非表示） |

- 各値には**信頼度（%）**を併記し、しきい値（既定 0.8）未満は CHECK 強調（確認画面の強調と同一基準）。
- ヘッダとして次も表示: ストリート / 表示モード（BB・チップ）/ SB・BB・アンティ（解決したブラインド
  レベル番号があれば併記）/ ポット / hero ハンド / 画像サイズ。
- 総チップ保存チェック（`chipConsistency`）が働いた場合は、その結果と補正した席を明示する。
- **失敗時も表示できる**こと（棄却された理由＝issue と、そこまでに読めた値を並べる）。

### 5.3 計算結果 `result`（★v3 で挙動変更）

- **判定ヒーロー**: PUSH/FOLD 大表示＋手札・ポジション・スタック・残り人数・EV。
- **Action tree（最重要）**: 全ポジションを常時1行ずつ表示。各行にインラインでアクション切替
  （FOLD / PU or CA or OC。前段状態で種別が自動で変わる）。**全ポジションの全条件を指定でき**、
  選んだノードのレンジ表が連動。全員フォールドで BB 手番の枝は "no decision" ロック。
- **BB のオールインへの受けレンジ**も tree の CA/OC ノードとして表示（ソルバー既算出）。
- **Frequency bar / 13×13 レンジ表（自分の手ハイライト）/ レンジ記法 / ICM equity（EQPre/EQPost/EQDiff）**。
- **記録は自動**（v3）。計算開始時点で記録が1件でき、完了時に確定する。結果画面に
  「記録する」ボタンは**置かない**。
- **公開レバー（v3・"記録レバー"からの置換）**: 結果画面のトグルは**「ホームで公開する」**の1本だけ。
  - オン → 一言コメント欄と確定ボタンが出る。確定で公開（スレッド作成）。
    ※トグルを触った瞬間に公開すると、コメントを書く前に出てしまうため、確定を1つ挟む。
  - オフに戻す → 公開を取り消す（スレッドと公開結果を削除。記録自体は残る）。
  - 既定はオフ（設定の「既定で公開」がオンなら既定オン）。
- **自分の選択は任意（v3）**: ALL IN / FOLD の2択に加え「未選択」を許す。選ぶとその場で保存され、
  EV loss が確定して集計に入る。**選ばなくても記録は残る**。あとから記録タブで選び直せる。
- 記録の削除は記録タブから行う（結果画面には置かない）。

### 5.4 記録タブ `records`

- **サーバが正・ローカルはキャッシュ**（§9.3）。端末を変えても記録は残る。
- 一覧の各行は次の状態を持つ:
  - **計算中**: スピナー＋「計算中…」。タップしても結果は開かない。
  - **完了**: 手札・ポジション・人数・判定・自分の選択（未選択なら「未選択」）・EV loss・日時。
  - **失敗 / 中断**: 理由と「再計算」ボタン（保存済みのスポットから解き直す）。
- 集計: **記録した場面数**（完了のみ）と **EV loss 累計**（自分の選択が入っている記録のみ）。
- 各記録の削除（サーバ・ローカル・画像を連鎖削除）。公開/非公開タグ表示。
  - 例外: **OCR が読めなかった／低信頼だった画像（保護画像）は削除しない**。精度改善の資産として
    無期限保持する（§7.2/§12）。保持することは設定画面の「保存について」で明示する。
    画像行が消えても解析ログ（`ocr_reads`）は残る（`image_id` は `on delete set null`）。

### 5.5 設定 `profile`
- プロフィール画像の選択・表示名/ユーザー名/パスワード変更。
- 公開のしかた（既定公開の ON/OFF）。
- **【v3 追加】保存について**の説明（何が・どこに・どれだけ保存されるか。§7.2/§12 の要約）。
- **アカウント削除**。ログアウト。
- （管理者のみ）**管理画面へ**の導線。

### 5.6 トレーニング（Drill）`drill` = 一旦伏せる
- タブは残し **"Coming Soon"** 表示。既存 Drill 実装はコード上は温存。

### 5.7 計算の非同期化（★v3 新設）

長い計算（6人・深いスタック）でユーザーを画面に縛らない。

1. **開始**: 条件確認の「この内容で計算する」を押すと、
   - 記録を1件作成し（状態 = **計算中**）、
   - **記録タブへ遷移**して先頭に「計算中」の行を出す。
   - 専用の `solving` 画面での待機は廃止する（画面遷移でユーザーを拘束しない）。
2. **計算中の自由**: ホーム・スレッド・記録・設定は自由に操作できる。計算は端末内 Web Worker で続く。
3. **同時に1件だけ**: 計算中は ICM タブの「写真を選ぶ」「手入力する」を無効化し、
   「計算中は次の画像を追加できません（完了までお待ちください）」と表示する。
4. **完了**: 記録を確定し、**トースト**「計算が完了しました」を出す。**タップで結果画面へ**。
   - 失敗時は「計算に失敗しました」＋タップで記録タブ（該当行に理由と再計算）。
   - トーストは数秒で自動的に消える。**アプリ内通知のみ**（OS プッシュ通知は使わない＝権限不要・ゼロ課金）。
5. **中断の扱い**: 計算はページ内 Worker なので、アプリを閉じる/リロードすると止まる。
   起動時に「計算中」のまま残っている自分の記録は**中断**に落とし、記録タブから**再計算**できる
   （スポットは保存済みのため解き直せる）。

## 7. 絶対条件：ゼロ課金

### 7.1 基本方針（v2 から不変）
- バックエンドは **Supabase 無料枠**（Auth / Postgres+RLS / Storage）。
  **クレジットカード未登録＝物理的に課金され得ない**。無料枠超過は「課金」ではなく「制限（通知後）」。
- **どのサービスにも支払い方法を登録しない**（Supabase / Cloudflare とも）。
- フロント配信は **Cloudflare Workers（カード未登録）**。
- 無料枠目安: DB 500MB / 認証 5万MAU / ストレージ1GB / 帯域5GB/月。
- Supabase の7日ポーズ対策: GitHub Actions 無料 cron で週1 warm ping。

### 7.2 画像を保存するための容量方針（★v3 新設）

スクショ原本は実測 **1.7〜3.1MB**。無圧縮・無期限で貯めると 1GB 枠を数百枚で使い切るため、
以下を**必須の仕様**とする。

1. **端末内で圧縮してからアップロード**: 長辺 1600px 以内・WebP（品質 0.8）へ変換。目標 **300KB 以下**。
   元のスクショは端末外へ送らない（送るのは圧縮版のみ）。
2. **保持期間**:
   - **OCR に成功した画像 … 90 日で自動削除**。
   - **OCR に失敗した画像・低信頼の画像 … 無期限保持**（OCR 強化の資産・§12）。
3. **総量の上限（保持期間より優先）**: 画像総量が **700MB** を超えたら、古い成功画像から順に削除する。
   失敗画像は保護し、失敗画像だけで **300MB** を超えた場合は管理画面に警告を出し、さつきが
   ローカルへ退避してから消す（自動では消さない）。
4. **削除の実行**: 週1の GitHub Actions（既存の warm ping と同じワークフロー）が Edge Function
   `purge-images` を呼ぶ。Edge Function 内で期限切れ・上限超過を判定して Storage と DB から削除する。
5. **DB 容量**: 解 JSON（`solution`）のサイズを実測した結果、**6人・62 ノードで 12〜13KB**
   （実ソルバー出力で測定・2026-09-09）。判定基準の 60KB を大きく下回るため**圧縮は行わない**
   （`encodeSolution` は恒等関数）。将来ノード数が増えた場合は `nodes[].hands` を 169bit マスクの
   base64（29文字）に畳む余地を残す。

## 8. セキュリティ / プライバシー方針

- 認証は**自作せず Supabase Auth**（実績あるハッシュ・セッション管理）。
- **Row Level Security (RLS)** で「自分の記録は自分だけ編集/削除」「公開記録は全員閲覧」を DB レベルで強制。
- **招待キー検証・上限・管理操作は必ずサーバ側**（Edge Function＋RLS）。クライアント判定に依存しない。
- 画像は Storage ポリシーで本人のみ書込み・サイズ/MIME 制限。
- 招待キーは**ハッシュ保存**・使い捨て・期限付き（§3）。
- **【v3】解析用スクショは非公開バケット**: スクショには他プレイヤーの実名が写るため、
  `spot-images` バケットは **private**（公開 URL を持たない）。閲覧できるのは
  **本人と管理者のみ**（RLS）で、表示には短命の署名 URL を使う。
  スレッド添付画像（`thread-images`）とプロフィール画像（`avatars`）は従来どおり公開バケット
  （利用者が能動的に共有したもの）。
- **【v3】利用者への明示**: 設定画面に「保存について」を置き、
  「計算した局面・結果・スクショ（圧縮版）はサーバに保存される」「スクショは本人と管理者しか見られない」
  「OCR がうまく読めなかった画像は精度向上のため保持される」ことを書く。

### 9.3 v3 新設テーブル

- **`images`**: id, owner, kind（`spot` = 解析元スクショ）, bucket, path, bytes, width, height, mime,
  sha256, created_at, **expires_at**（null＝無期限）, **protected**（true＝自動削除しない＝OCR 失敗画像）。
- **`ocr_reads`**（OCR 改善データ基盤・§12）: id, owner, image_id, result_id（null 可）, ok,
  display_mode, street, issues(jsonb), low_confidence(jsonb), **raw_reads(jsonb)**, state(jsonb, 成功時),
  **final_state(jsonb**, 実際に計算に使われた入力）, **corrections(jsonb**, OCR 出力→最終入力の差分）,
  app_version, ocr_version, device(jsonb: UA・DPR・画像寸法・アスペクト), created_at。

### 9.4 記録の同期規則（サーバが正）
- 計算開始で `results` に `status='solving'` を **サーバへ挿入**し、同じ内容をローカル IndexedDB にも書く。
- 完了・失敗・自分の選択・公開の各更新はサーバへ書き、成功したらローカルを更新する。
- 記録タブはまずローカルキャッシュを描画し、サーバ取得が済んだら差し替える（体感速度と正しさの両立）。
- オフライン等でサーバ書込みに失敗した記録は `pending` としてローカルに残し、次回オンライン時に再送する
  （`client_id` で冪等）。

## 12. OCR 改善データ基盤（★v3 新設）

**目的**: 実利用で集まるスクショ（とりわけ失敗例）を資産化し、OCR を継続的に強化する。

### 12.1 何を記録するか
OCR を通した画像は**成功・失敗を問わず** `ocr_reads` に1行記録する（画像は §7.2 の方針で保存）。

- **入力側**: 画像参照・画像寸法とアスペクト比・端末情報（UA / DPR）・アプリ版 / OCR 版。
- **出力側**: `ok`・表示モード・ストリート・**席ごとの生読み取り（値＋信頼度）の全量**・
  低信頼フィールド一覧・issue 一覧・復元できた `state`。
- **正解に近づく情報**: 利用者が条件確認画面で**直した値の差分**（`corrections`）と、
  実際に計算に使われた `final_state`。**これが暗黙の正解ラベル**になる。

### 12.2 解析しやすさのための形（重要）
- 席ごとの値は**固定スキーマの配列**で保存する:
  `raw_reads.seats[] = { id, pos, isHero, isButton, occupancy:{value,conf}, action:{value,conf}, stack:{value,conf}, bet:{value,conf} }`。
  （JSON の形を回ごとに変えない。これを守らないと後段の一括解析が書けない）
- ヘッダ値も同形: `street`, `blinds.sb/bb`, `ante`, `pot`, `heroHand`, `displayMode`, `blindChips`。
- 失敗の分類キー `issues[]` は**メッセージ本文ではなく安定した理由コード**を併記する
  （例 `street_not_preflop` / `display_mode_chips` / `out_of_scope_raise` / `out_of_scope_limp` /
  `walk` / `seat_read_failed` / `checksum_mismatch`）。集計はコードで行う。
- インデックス: `(ok, created_at desc)` / `(display_mode)` / `((device->>'aspect'))` を張り、
  「どの機種・どの表示モードで落ちているか」を1クエリで出せるようにする。

### 12.3 解析の回し方（運用）
- ローカル用の取得スクリプト `packages/ocr/scripts/pullFailures.ts`（service_role キーは
  ローカル環境変数のみ・リポジトリに置かない）で、失敗画像と `ocr_reads` の JSON を
  `packages/ocr/local-fixtures/`（gitignore 済み）へ落とす。
- 既存の較正ハーネス（`verifyFrame.ts` / `tuneField.ts`）にそのまま噛ませ、
  **AI 目視 vs OCR 出力の照合**（[[ocr-accuracy-verification]] の鉄則）で原因を切り分ける。
- 管理画面には件数と内訳だけを出す（画像の一覧表示はプライバシー上つくらない）。
